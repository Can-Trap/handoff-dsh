# `_adherence.oxlintrc.json` — derivation

A generated oxlint config that enforces design-system adherence **in the target codebase**. It is
what turns "implement it faithfully" from an opinion into something CI can check.

Generated by `scripts/_adherence.js` from `_ds_manifest.json` plus each component's `.d.ts`.
**Never hand-write it.** If the source project already ships one, phase 01 mirrors it byte-for-byte
instead of regenerating.

Rule shapes below were recovered by diffing two real generated configs — one from a project-local
design system, one from a published library — and the generator reproduces all 22 rules of the
project-local sample exactly, selectors and messages alike.

## Shape

```jsonc
{
  "plugins": ["react", "import"],
  "rules": {
    "react/forbid-elements": ["warn", { "forbid": [...] }],
    "no-restricted-imports":  ["warn", { "patterns": [{ "group": [...], "message": "..." }] }],
    "no-restricted-syntax":   ["warn", ...rules]
  },
  "overrides": [{ "files": ["**/index.js"], "rules": { "no-restricted-imports": "off" } }],
  "x-omelette": { "components": { "<Name>": { "replaces": [...] } }, "tokens": ["--..."] }
}
```

Severity is `warn` throughout — advisory, never build-breaking.

## Rule by rule

### 1. `x-omelette.components[Name].replaces[]`

Which native element a component supersedes. This is **library-declared metadata, not static
analysis**: the published-library design system declares `Button->button`, `Dialog->dialog`,
`Input->input`; the project-local one declares **none at all**, despite shipping `Button`, `Input`,
`Select` and `Textarea`.

So: read `components[].replaces` or a manifest-level `replaces` map. Never guess. An empty array is
a correct, common answer.

### 2. `react/forbid-elements`

One `{element, message}` per non-empty `replaces`, sorted by element:

```
Use <Button> from the design system instead of <button>.
```

### 3. `no-restricted-imports`

`group[]` = `dirname(component.sourcePath) + "/**"` for every manifest component, deduped, in
manifest order. One fixed message:

```
Import design-system components from 'index.js', not component internals.
```

The `**/index.js` override exists so the barrel file itself may import the internals.

### 4. `no-restricted-syntax` — three fixed selectors

```
Literal[value=/#[0-9a-fA-F]{3,8}\b/]      Raw hex color — use a design-system color token via var().
Literal[value=/\b\d+px\b/]                Raw px value — use a design-system spacing token via var().
Literal[value=/font-family\s*:\s*(?!['\"]?(?:<FONTS>))/i]
                                          Font not provided by the design system. Available: <FONTS>.
```

`<FONTS>` is the pipe-joined allowlist from `manifest.fonts` + `manifest.brandFonts`. The font rule
is omitted entirely when the design system declares no fonts.

### 5. `no-restricted-syntax` — one rule per component

```
JSXOpeningElement[name.name='<Name>'] > JSXAttribute > JSXIdentifier[name!=/^(?:<props>|key|ref|className|style|children)$/]
<Name> doesn't accept that prop. Declared props: <props, comma-joined>.
```

`<props>` are the members of the `<Name>Props` interface **in declaration order** — that order is
what the message prints. The tail `key|ref|className|style|children` is always appended to the
allowlist and never appears in the message.

Components are emitted **sorted alphabetically**. A component whose props cannot be read (a
collapsed design system ships no `.d.ts`) is skipped rather than emitted empty.

### 6. `no-restricted-syntax` — inline string-literal unions

A prop whose type is an **inline** union of string literals also constrains its value:

```
JSXOpeningElement[name.name='Separator'] > JSXAttribute[name.name='variant'] > Literal[value!=/^(?:divider|vein)$/]
<Separator> variant must be one of 'divider' | 'vein'.
```

**Inline only.** `variant?: "divider" | "vein"` gets a rule; `variant?: ButtonVariant` does not,
even though the alias resolves to a union — the generator does not chase aliases, and matching that
behavior keeps output stable. These rules follow their component's prop rule, in prop order.

### 7. `x-omelette.tokens[]`

Every custom-property name from `manifest.tokens[].name`, deduped and sorted.

## `.d.ts` parsing — two traps

**Do not track `<` and `>` as nesting.** The `>` in an arrow type unbalances the depth counter and
silently swallows every member declared after it:

```ts
onChange?: (next: boolean) => void;   // the `>` here ate the next prop
scale?: number;                       // ...this one
```

Track only `{ [ (` / `} ] )`. Generics need no tracking because a member's type annotation is
skipped wholesale.

**Quoted keys are skipped, not fatal.** `"aria-label"?: string` is not a bare identifier, so it is
left out of the allowlist — which is the correct lint behavior — while the rest of the interface is
still emitted.

## One deliberate divergence

The upstream generator skips components declared as bare `FC<XProps>` while keeping
`React.FC<XProps>` ones — a quirk of its own regex, not a design decision. We emit a rule for
**every exported interface**, which is a strict superset: the same 22 rules plus the two components
upstream dropped. Nothing is lost, two more components get linted.
